# 네이버 클라우드(NCP) 배포·업데이트 가이드

연구실 PC(WSL)에서 개발하던 DFT-Workbench 를 네이버 클라우드 서버에도 올려
같은 프로그램을 **어디서나 접속**하고, GitHub 에 올린 새 코드를 **한 줄로 업데이트**하는 방법입니다.

```
 [연구실 PC · WSL]  --- git push --->  [GitHub]  --- git pull --->  [NCP 서버 · Ubuntu]
   개발·테스트                      clsrn0319-ui/DFT-Workbench       ./scripts/update.sh
                                                                     systemd 서비스 rhobench
                                                                     nginx 80/443 → 8000
                                                                     브라우저: http(s)://<공인 IP 또는 도메인>/
```

동작 원리는 WSL 과 같습니다 — 코드·계산 엔진·데이터 구조 모두 동일하고, 다른 점은
서버가 **systemd 서비스**로 항상 떠 있고 **nginx** 가 앞에서 80/443 을 받는다는 것뿐입니다.

---

## 1. 서버 만들기 (NCP 콘솔)

| 항목 | 권장 | 이유 |
|---|---|---|
| 서비스 | Server (VPC) | 일반 가상 서버 |
| OS | **Ubuntu Server 22.04 (또는 24.04)** | PySCF 는 리눅스 전용. 설치 스크립트가 apt 기준 |
| 사양 | **vCPU 8 이상 · 메모리 32 GB 이상** (High-CPU 또는 Standard) | DFT 는 CPU·메모리 집약. 표준 정확도 분자 하나가 수 분~수십 분. 정밀·Li⁺ 참조 클러스터는 코어가 많을수록 빠름 |
| 스토리지 | 100 GB 이상 (SSD) | 원본 로그가 작업당 수백 KB~수십 MB. 캠페인 수백 건이면 수십 GB |
| 공인 IP | 할당 | 외부 접속용 |
| 인증키 | 새로 만들어 .pem 보관 | SSH 접속 |

> 사양은 «계산 시간 ↔ 비용» 트레이드오프입니다. 배치 스크리닝을 자주 돌리면 16 vCPU 가 편하고,
> 결과 열람 위주라면 4 vCPU 로도 뜹니다(계산은 느림). 필요할 때 스펙을 올릴 수 있습니다.

### ACG (방화벽) — 인바운드 규칙

| 프로토콜 | 포트 | 허용 IP | 용도 |
|---|---|---|---|
| TCP | 22 | 내 IP (연구실·집) | SSH |
| TCP | 80 | 연구실 IP 대역 (또는 0.0.0.0/0) | 웹 접속 (HTTP) |
| TCP | 443 | 연구실 IP 대역 (또는 0.0.0.0/0) | 웹 접속 (HTTPS, 도메인 있을 때) |
| — | 8000 | **열지 않음** | 내부 포트 — nginx 만 접근 |

아웃바운드는 기본(전체 허용)으로 두어야 apt·pip·GitHub·PubChem 조회가 됩니다.

## 2. 최초 설치 (한 번)

SSH 로 접속한 뒤(NCP 콘솔 «서버 관리 → 관리자 비밀번호 확인» 또는 .pem):

```bash
ssh -i key.pem ubuntu@<공인 IP>      # 계정은 이미지에 따라 ubuntu 또는 root

sudo apt update && sudo apt install -y git
git clone https://github.com/clsrn0319-ui/DFT-Workbench
cd DFT-Workbench
git checkout claude/solvent-air-environment-settings-ow1ylt   # 현재 개발 브랜치 (main 으로 합치면 생략)
./scripts/ncp_setup.sh
```

`ncp_setup.sh` 가 순서대로 처리합니다 (이미 끝난 단계는 건너뜀):

1. apt 패키지 — git · python3-venv · nginx · curl
2. `.venv` 생성 + PySCF·RDKit·FastAPI 설치 (`setup.sh`, 5~10분)
3. `/etc/rhobench.env` 생성 — 접속 비밀번호를 묻습니다 (Enter = 무작위 발급 → 로그에 한 번 출력)
4. systemd 서비스 `rhobench` 등록·시작 (부팅 시 자동 시작, 죽으면 자동 재시작)
5. nginx 리버스 프록시 (80 → 127.0.0.1:8000)
6. 접속 주소 안내

끝나면 브라우저에서 `http://<공인 IP>/` 로 접속해 비밀번호를 넣습니다.

### 도메인 + HTTPS (권장)

공인 IP 만으로 쓰면 HTTP 라 세션 쿠키가 평문으로 오갑니다. 도메인이 있으면 무료 인증서를 붙이세요:

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo sed -i 's/server_name _;/server_name rhobench.example.com;/' /etc/nginx/sites-available/rhobench
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d rhobench.example.com     # 자동 갱신까지 설정됨
```

도메인이 없으면 ACG 에서 80 번의 허용 IP 를 연구실 대역으로 제한하는 것으로 대신합니다.

## 3. 업데이트 흐름

### 연구실 PC 에서 (개발)

```bash
# WSL
cd ~/DFT-Workbench
git add -A && git commit -m "…"
# Windows Git Bash (WSL 의 자격증명 연동이 안 될 때)
cd //wsl.localhost/Ubuntu/home/keti/DFT-Workbench && git -c safe.directory='*' push origin <브랜치>
```

### NCP 서버에서 (배포)

```bash
cd ~/DFT-Workbench
./scripts/update.sh
```

`update.sh` 는

1. GitHub 의 새 커밋을 확인해 **무엇이 바뀌는지 먼저 보여주고**
2. `git pull` (requirements.txt 가 바뀌었으면 패키지 재설치)
3. `--test` 를 주면 가벼운 테스트(약 15초)를 돌려 실패하면 이전 커밋으로 되돌리고
4. **실행 중인 작업·캠페인이 없을 때까지 기다렸다가** (60초마다 확인)
5. 서비스를 재시작하고 60초 안에 응답이 없으면 **이전 커밋으로 롤백**합니다.

| 옵션 | 뜻 |
|---|---|
| `--check` | 바뀌는 커밋만 보고 끝 |
| `--now` | 기다리지 않고 바로 재시작 (진행 중 작업은 «서버 재시작으로 중단됨», 캠페인은 자동 재시도) |
| `--test` | 재시작 전 테스트 |
| `--ref main` | 특정 브랜치/커밋으로 |
| `--no-restart` | 코드만 받고 재시작은 나중에 |

같은 스크립트를 WSL 에서 써도 됩니다 — systemd 가 없으면 기존 uvicorn 을 찾아 환경변수를 물려받아 다시 띄웁니다.

> 계산 중 재시작하면 그 작업은 실패 처리됩니다. 캠페인은 `data/campaigns.json` 체크포인트에서
> 이어지고 실패한 후보를 자동 재시도하지만, 단건 작업은 «재시도» 버튼을 눌러야 합니다.
> 기본(대기 모드)으로 쓰면 이 문제가 없습니다.

## 4. 백업

결과·캠페인·비밀번호 해시·Li⁺ 참조 캐시가 모두 `data/` 에 있습니다.

```bash
./scripts/backup_data.sh                        # backups/rhobench-data-날짜.tar.gz
./scripts/backup_data.sh --no-logs --keep 14    # 원본 로그 제외, 14개만 보관
```

### Object Storage 로 자동 백업

1. NCP 콘솔 → Object Storage → 버킷 생성 (예: `rhobench-backup`)
2. 마이페이지 → 인증키 관리 → Access Key / Secret Key 발급
3. 서버에서

```bash
sudo apt install -y awscli
aws configure        # 키 입력, region: kr-standard, output: json
./scripts/backup_data.sh --upload rhobench-backup
```

4. 매일 새벽 3시 (`crontab -e`):

```
0 3 * * * /home/ubuntu/DFT-Workbench/scripts/backup_data.sh --upload rhobench-backup --keep 14 >> /home/ubuntu/backup.log 2>&1
```

복원은 tar 를 풀어 `data/` 를 덮어쓰고 서비스를 재시작하면 됩니다. 연구실 PC 의 `data/` 를
그대로 복사해 올려도 결과가 이어집니다 (`scp -r data ubuntu@<IP>:~/DFT-Workbench/`).

## 5. 운영 명령

| 할 일 | 명령 |
|---|---|
| 상태 | `sudo systemctl status rhobench` |
| 실시간 로그 | `sudo journalctl -u rhobench -f` |
| 최초 발급 비밀번호 확인 | `sudo journalctl -u rhobench \| grep -A3 '접속 비밀번호'` |
| 비밀번호 변경 | `sudo nano /etc/rhobench.env` → `RHOBENCH_ACCESS_PASSWORD=새값` → `sudo systemctl restart rhobench` |
| 워커 수·동시 작업 수 조정 | `/etc/rhobench.env` 의 `RHOBENCH_WORKERS`, `RHOBENCH_MAX_ACTIVE_JOBS` (vCPU 16 이면 워커 2, `OMP_NUM_THREADS=8`) |
| 재시작 / 중지 | `sudo systemctl restart rhobench` / `sudo systemctl stop rhobench` |
| CPU·메모리 확인 | `htop` (`sudo apt install htop`), 화면의 «계산 모니터» |
| 디스크 확인 | `df -h`, `du -sh ~/DFT-Workbench/data/logs` |
| 시험 작업 정리 | `.venv/bin/python -m scripts.prune_jobs --list` |

서버 시간대가 UTC 이면 로그 시각이 9시간 어긋납니다: `sudo timedatectl set-timezone Asia/Seoul`.

## 6. 두 환경을 함께 쓸 때

- **코드**는 GitHub 이 기준입니다. 어느 쪽에서 고쳤든 push → 다른 쪽에서 `update.sh`.
- **데이터**는 서로 독립입니다. 연구실 PC 결과를 클라우드에서도 보려면 `data/` 를 복사하거나,
  클라우드를 «공용 서버»로 정하고 연구실에서는 브라우저로만 접속하는 편이 관리가 쉽습니다.
- 브라우저별 저장소(물질 보관함·용매 라이브러리·레이더 축)는 접속하는 PC 의 브라우저에 남습니다.
- 프로토콜 카드 해시가 같으면 두 환경의 결과를 직접 비교할 수 있습니다 (같은 커밋·같은 설정).

## 7. 문제 해결

| 증상 | 확인 |
|---|---|
| `ncp_setup.sh` 1단계에서 apt 실패 | ACG 아웃바운드 허용, `ping -c 2 archive.ubuntu.com` |
| 서비스가 뜨지 않음 | `sudo journalctl -u rhobench -n 50` — 보통 패키지 누락(`./scripts/setup.sh` 재실행) 또는 포트 충돌 |
| 브라우저에서 «502 Bad Gateway» | 서비스가 아직 뜨는 중(30초 대기) 또는 죽음 — 위 로그 확인 |
| 접속은 되는데 비밀번호 거부 | `/etc/rhobench.env` 값과 다름. 값을 다시 쓰고 `systemctl restart rhobench` |
| 다른 PC 에서 접속 안 됨 | ACG 80/443 허용 IP, 공인 IP 할당 여부 |
| 계산이 «서버 재시작으로 중단됨» | `Restart=always` 로 자동 재시작된 경우(OOM 등). `dmesg \| grep -i kill`, 메모리 상향 또는 `RHOBENCH_MAX_ATOMS` 하향 |
| 디스크 부족 | `data/logs` 정리, 전문가 설정 «원본 로그 수준 = 간략», 백업 `--no-logs` |
| `update.sh` 가 계속 대기 | 활성 작업이 있는 것. 화면 «계산 모니터» 확인 후 필요하면 `--now` |
| 롤백됨 | 새 커밋에서 서버가 못 뜬 것. `journalctl` 의 트레이스백을 보고 연구실에서 고쳐 다시 push |
