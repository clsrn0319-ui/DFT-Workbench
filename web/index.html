1. 검토 범위와 제한

파일은 React 및 SmilesDrawer 등 의존성을 한 HTML에 번들링한 형태입니다. 화면 구조, 상태 저장, 모의 작업 파이프라인, PubChem 조회, 입력 처리, 접근성 마크업을 검토했습니다.

보안 정책상 로컬 file:// 페이지를 브라우저에서 실행하지 못해 실제 클릭·반응형·렌더링 테스트는 수행하지 않았습니다. 따라서 아래 내용은 코드에서 직접 확인된 사항과 그에 따른 합리적 위험 평가이며, 배포 전 실제 브라우저 테스트가 추가로 필요합니다.

2. 잘된 점

  • 계산 결과를 PUBLISHED 게이트 이후에만 수치로 노출하려는 정보 구조가 명확합니다.
  • 구조 버전 변경 시 기존 계산 결과를 구분하고 삭제 영향도를 확인하는 흐름이 포함되어 있습니다.
  • 단위·기준전극·계산 조건·검증 메모를 결과 패키지에 포함하려는 설계가 재현성 방향에 부합합니다.
  • 차트에 aria-label과 텍스트 라벨을 일부 제공하고 색각 친화 프리셋을 마련한 점은 좋은 출발입니다.
  • 물질·용매·비교·물성 사전·시각화 설정으로 기능 영역이 구분되어 사용자 여정이 비교적 선명합니다.

3. 주요 문제점과 개선안

P0I-01. 모의 계산값과 실제 계산값의 경계가 충분히 강하지 않음

확인 근거 — 작업 진행률과 검증 전환에 Math.random()이 사용되고, 결과는 '브라우저 내 모의 엔진'이 생성합니다. 그러나 결과 화면은 'PUBLISHED 서버 계산값'이라고 표현합니다.

영향 — 연구자가 모의값을 실제 DFT 또는 검증 완료값으로 오인하면 후보 순위와 실험 계획이 왜곡될 수 있습니다.

개선 제안 — 모의 모드에서는 모든 결과 카드·차트·내보내기 파일에 SIMULATED 워터마크와 provenance 필드를 강제하십시오. 실제 모드와 데이터 저장소를 분리하고, PUBLISHED는 서버 서명된 검증 결과에만 부여하십시오.

완료 기준 — 모의 데이터가 실제 데이터와 동일한 상태·색상·내보내기 형식으로 표시되지 않으며, JSON에 data_origin, engine_version, calculation_id, validated_by가 필수로 포함됩니다.

P0I-02. 존재하지 않는 서버 구성요소가 항상 정상으로 표시됨

확인 근거 — 사이드바와 서버 상태 카드에서 FastAPI, Redis/Celery, RDKit·xTB·PySCF, PostgreSQL·MinIO가 모두 고정된 녹색 점과 '정상'으로 표시됩니다.

영향 — 실제 백엔드 연결 여부와 무관한 정상 표시는 운영·연구 판단을 오도하고 장애 탐지를 방해합니다.

개선 제안 — 프로토타입에서는 '미연결/모의' 중립 상태로 표시하십시오. 상용 버전은 /health 응답, 최근 확인 시각, 구성요소별 상태, 지연 시간과 오류 사유를 사용해 표시해야 합니다.

완료 기준 — 백엔드가 없을 때 녹색 정상 상태가 나타나지 않고, 상태가 실제 health check 결과와 일치하며 마지막 확인 시간이 표시됩니다.

P0I-03. SMILES 파싱 오류 경로의 DOM XSS 가능성

확인 근거 — 사용자 입력 SMILES가 파싱 실패 시 SVG의 innerHTML 문자열에 직접 삽입됩니다: '구조 파싱 실패: ${t.slice(0,30)}'.

영향 — 악성 문자열이 마크업으로 해석되면 임의 DOM 삽입 또는 스크립트 실행으로 이어질 수 있습니다. 가져온 데이터나 공유 데이터가 연결되면 위험이 커집니다.

개선 제안 — innerHTML을 제거하고 SVG text 노드를 createElementNS/textContent로 생성하십시오. 입력 스키마를 허용 문자·길이·문법으로 검증하고, CSP를 추가하십시오.

완료 기준 — 보안 테스트 문자열이 텍스트로만 렌더링되고 DOM 노드가 생성되지 않으며, 정적 분석에서 사용자 입력이 innerHTML로 흐르는 경로가 0건입니다.

P1I-04. 브라우저 localStorage 중심의 데이터 내구성 부족

확인 근거 — 전체 애플리케이션 상태를 localStorage 하나에 저장하며 JSON.parse 오류는 빈 catch로 무시됩니다. 손상 시 기본 데이터로 조용히 복귀합니다.

영향 — 용량 한도, 동시 탭 충돌, 저장 실패, 브라우저 데이터 삭제로 계산 이력과 사용자 입력을 잃을 수 있습니다.

개선 제안 — 연구 데이터는 서버 DB와 객체 저장소에 저장하고 revision/ETag 기반 충돌 제어를 적용하십시오. 로컬 저장은 임시 초안으로 제한하고, 마이그레이션 버전·백업·복구 알림을 추가하십시오.

완료 기준 — 저장 실패가 사용자에게 명시되고, 새로고침·다중 탭·버전 업그레이드·localStorage 손상 테스트에서 데이터가 보존 또는 복구됩니다.

P1I-05. 1초 주기 전체 상태 직렬화로 인한 성능·수명 문제

확인 근거 — 작업 진행을 위해 매초 tick을 발생시키고, 모든 상태 변경마다 전체 상태를 JSON.stringify하여 localStorage에 기록합니다.

영향 — 물질·작업·결과가 늘면 메인 스레드 정지, 입력 지연, 저장 한도 초과가 발생할 수 있습니다.

개선 제안 — 진행 상태와 영구 데이터를 분리하고 저장을 debounce하십시오. 작업 상태는 서버 이벤트(SSE/WebSocket) 또는 폴링으로 받고, 변경된 엔터티만 저장하십시오.

완료 기준 — 1,000개 물질/10,000개 작업 조건에서도 입력 반응과 스크롤이 유지되고, 초당 전체 상태 쓰기가 발생하지 않습니다.

P1I-06. PubChem을 프런트엔드에서 직접 호출

확인 근거 — SMILES를 포함한 PubChem REST URL을 브라우저가 직접 호출하며 8초 타임아웃만 적용합니다. 코드도 CORS·보안망·오프라인 실패를 예상합니다.

영향 — 기관망 정책, CORS, 레이트리밋, 외부 서비스 장애에 따라 기능이 불안정하고 질의 정보가 외부로 직접 전송됩니다.

개선 제안 — 백엔드 프록시를 사용해 캐시, 속도 제한, 재시도, 감사 로그, 개인정보·연구정보 정책을 통제하십시오. 사용자에게 외부 조회 사실도 고지하십시오.

완료 기준 — 오프라인/레이트리밋/타임아웃 상황에서 일관된 오류가 표시되고, 동일 SMILES 재조회는 캐시를 사용하며 외부 전송 정책이 문서화됩니다.

P1I-07. 과학적 재현성 메타데이터가 충분히 강제되지 않음

확인 근거 — 결과 JSON에는 일부 method/basis/solvent 정보가 있으나 입력 구조 해시, 전하·다중도, 소프트웨어·컨테이너 버전, 수렴 임계값, 원시 로그 해시, 검증자 정보의 필수성이 보장되지 않습니다.

영향 — 동일 결과의 재계산과 감사, 논문·특허 근거 추적이 어렵습니다.

개선 제안 — Calculation Manifest 스키마를 만들고 입력 구조·환경·엔진·파라미터·하드웨어·로그·산출물 해시를 불변 객체로 저장하십시오.

완료 기준 — 어떤 PUBLISHED 결과도 manifest 검증 없이 생성되지 않고, manifest만으로 동일 계산을 재실행할 수 있습니다.

P1I-08. 검증 게이트가 시간 경과 기반 모의 전환에 가까움

확인 근거 — VALIDATING 상태는 tick 횟수가 누적되면 전환되며 실제 SCF 수렴, 허수 진동수, 구조 동일성, 전하·다중도 검증과 연결되지 않습니다.

영향 — 검증이라는 명칭이 품질 보증을 암시하지만 실제 물리·수치 기준을 충족하지 않을 수 있습니다.

개선 제안 — Validator를 독립 서버 단계로 구현하고 각 검사 결과를 구조화하십시오. 실패 원인, 임계값, 재시도 정책과 승인 권한을 명시하십시오.

완료 기준 — PUBLISHED 전환은 필수 검증 규칙 전부의 machine-readable PASS와 승인 기록이 있을 때만 가능합니다.

P1I-09. 키보드 접근성과 상태 알림이 불완전

확인 근거 — workflow의 li와 최근 물질 테이블 행에 onClick이 있으나 button/link 역할, tabIndex, 키보드 이벤트가 없습니다. aria-current, aria-live, focus-visible 스타일도 확인되지 않습니다.

영향 — 키보드·스크린리더 사용자는 주요 탐색과 작업 상태 변화를 이용하기 어렵습니다.

개선 제안 — 클릭 가능한 비대화형 요소를 button/link로 교체하고 현재 메뉴에 aria-current를 적용하십시오. 작업 진행·오류에는 aria-live를 사용하고 명확한 포커스 링을 추가하십시오.

완료 기준 — 키보드만으로 모든 화면과 행 작업을 수행할 수 있고, axe/WCAG 2.2 AA 자동 검사에서 중대 오류가 없습니다.

P1I-10. 작은 보조 텍스트와 앰버 색상의 대비 부족

확인 근거 — 기본 muted #898781은 흰색 대비 3.59:1이고 pin #D97706은 3.19:1입니다. 11~12px 텍스트와 상태 배지에 사용됩니다.

영향 — WCAG AA의 일반 텍스트 4.5:1 기준을 충족하지 못해 저시력 환경에서 상태와 설명이 흐려집니다.

개선 제안 — 보조 텍스트 색을 더 어둡게 조정하고 앰버는 배경·아이콘에만 사용하거나 더 진한 텍스트 색을 병행하십시오. 테마 편집 시 대비를 자동 검증하십시오.

완료 기준 — 모든 일반 텍스트는 4.5:1 이상, 큰 텍스트·비텍스트 UI는 3:1 이상이며 라이트·다크·색각 친화 테마 모두 통과합니다.

P2I-11. 모바일·좁은 화면 내비게이션 대응 부족

확인 근거 — 사이드바가 232px 고정 폭·100vh sticky이며, 그리드만 일부 단일 열로 전환됩니다. 사이드바 접기/오버레이용 미디어 규칙은 없습니다.

영향 — 작은 화면에서 콘텐츠 폭과 조작 영역이 압축되고 가로 스크롤 또는 가독성 저하가 발생할 가능성이 큽니다.

개선 제안 — 768px 이하에서는 내비게이션을 드로어로 전환하고, 표는 중요 열 우선·카드 변환·가로 스크롤 안내를 제공하십시오.

완료 기준 — 360px, 768px, 1024px에서 콘텐츠 가림·이중 스크롤·수평 오버플로가 없고 주요 작업이 44px 터치 타깃을 충족합니다.

P2I-12. 단일 549KB 번들 파일로 인한 유지보수·테스트 한계

확인 근거 — 스타일, 데이터, React 런타임, 상태 관리, 도메인 로직, UI가 하나의 minified HTML 파일에 포함되어 있습니다.

영향 — 도메인 규칙 변경의 영향 범위가 불명확하고 단위 테스트, 코드 리뷰, 의존성 업데이트, 보안 패치가 어렵습니다.

개선 제안 — Vite/React 프로젝트로 원본을 복원하고 domain, api, store, components, validators, fixtures를 분리하십시오. TypeScript, schema validation, unit/e2e 테스트와 SBOM을 도입하십시오.

완료 기준 — CI에서 lint/typecheck/unit/e2e/security scan을 실행하며 계산 규칙과 UI 변경을 독립적으로 테스트할 수 있습니다.

5. 배포 전 최소 체크리스트

  • 모의값과 실제값이 상태·색·파일·API 수준에서 분리되어 있는가
  • 서버 상태가 실제 health check와 마지막 확인 시각을 반영하는가
  • 사용자 입력이 innerHTML 또는 검증되지 않은 URL·CSS로 전달되지 않는가
  • 결과마다 불변 Calculation Manifest와 원시 로그·산출물 해시가 존재하는가
  • 검증 규칙의 PASS 기록 없이는 PUBLISHED가 불가능한가
  • 저장 실패·동시 수정·오프라인·외부 API 장애 시 복구 가능한가
  • 키보드, 스크린리더, 대비, 360px 반응형 테스트를 통과하는가
  • 대표 과학 시나리오에 대한 golden dataset 회귀 테스트가 있는가

6. 결론

이 프로토타입은 복잡한 DFT 워크플로우를 한 화면군으로 설명하고 후보·계산·검증·비교의 사용자 여정을 검증하는 데 충분한 가치가 있습니다. 다음 단계의 핵심은 기능 추가보다 신뢰 경계를 먼저 세우는 것입니다. 모의값 표시, 실제 인프라 상태, 검증 근거, 데이터 provenance가 명확히 분리되어야 이후의 UI 개선과 백엔드 연동이 연구 의사결정에 안전하게 연결됩니다.
